## 1. Introduction

### 1.1 背景：從「聽得懂」到「做得到」

大型語言模型（LLM）讓機器人能以自然語言接收任務。從 SayCan 以技能可行性約束語言計畫 [2]、ReAct 交替推理與工具行動 [1]，到 ROS-LLM 讓非專家以對話設計 ROS 機器人行為 [14]，語言介面正快速進入機器人系統。對移動機器人而言，LM-Nav 已展示以預訓練語言、視覺與導航模型串接長距離戶外導航 [16]；2025 年的研究則把 LLM 與 ROS 2 整合時的延遲列為需要量測的問題 [3]。

然而，語言上合理的指令不等於可以安全執行的動作 [2]。LLM 可能把模糊的地點指稱當成確定目標，可能提出地圖上不存在的位置，也可能在沒有執行證據時宣稱任務完成。近期研究開始為 LLM 機器人加上「先問再做」的不確定性對齊 [13] 與安全護欄 [15]，顯示「理解語言」與「可靠執行」之間仍有一段需要工程設計與實驗驗證的距離。

### 1.2 本專題場景

本專題的場景是大學實驗室中的 TurtleBot3 Burger。使用者多為剛接觸 ROS 2 的學生：他們想說「去 A 門口」，而不是在 RViz 中手動點選座標。底層導航已有成熟的 Nav2 [4] 與 SLAM Toolbox [5]；真正的缺口在任務層——要去哪裡、現在能不能出發、結果到底是什麼。

### 1.3 問題：text-to-goal 的三個失效模式

若把中文指令直接轉成導航目標，至少會出現以下三種失效：

- **F1 歧義與不存在的目標**：「去門口」對應兩個已登錄門口；「去咖啡廳」根本不在地圖上。
- **F2 失效狀態下出發**：雷射資料過期、TF 中斷、已有任務執行中，仍送出新目標。
- **F3 無依據的回報**：取消、逾時或失敗被說成「到達」；取消請求被接受就被當成已停止。

**問題定義**：給定中文任務 Q、已登錄地點表 K、地圖與機器人狀態 S，系統必須決定 (a) 是否需要澄清或拒絕，(b) 是否滿足派送條件，(c) 任務終止時應回報哪一種狀態，且每個決定都有可核對的證據。

### 1.4 方法概述

本專題提出一個證據導向的任務 Agent，原則是 **「LLM 負責理解與協調；白名單、狀態檢查、Nav2 與事件紀錄負責判斷與證據」**。三個機制對應三個失效模式：

| 失效模式 | 設計機制 | 研究問題 |
|---|---|---|
| F1 歧義／不存在目標 | Schema + 地點白名單 + Clarification Loop | **RQ1** 澄清是否降低歧義／未知目標的不當派送？ |
| F2 失效狀態出發 | Readiness Gate（定位、雷射、TF 時效與任務互斥） | **RQ2** 狀態檢查是否降低故障情境下的不當派送？ |
| F3 無依據回報 | Evidence-based Reporting（依 action 結果 + 觀測姿態） | **RQ3** 依事件回報是否提高回報正確率？延遲代價多少？ |

LLM 只能輸出四種 intent 與已登錄地點 ID，透過六個白名單工具與 Nav2 互動，不能產生座標、輪速或修改安全參數；低延遲停止由底層負責，不等待 LLM。

### 1.5 貢獻

1. **系統**：一套在 ROS 2／Nav2 上的受限工具 Agent，含中文澄清、派送前狀態檢查與證據回報，並以 OpenSpec 規格（4 個 capability、17 條 requirement）定義可驗收行為。
2. **資料**：60 筆標註的繁體中文室內導航指令，涵蓋明確、歧義、未知、取消、複合與越權／矛盾六類，依語意模板分組切分以避免洩漏。
3. **評估**：在固定 Nav2 條件下比較固定選單（B0）、直接語言轉目標（B1）與完整 Agent（B2），並以兩項消融把語言層、導航層與回報層的成效分開量測。

**本專題不宣稱**首次提出 LLM 導航，也不改進 Nav2 的規劃或控制演算法；定位為教學與實驗室場景的系統整合與可靠性評估。目前尚無實驗結果，所有效益均待驗證。

### 1.6 範圍

第一版限單台 Burger、單一室內平面、預建地圖與人工命名地點；不做任意物體辨識、取放、多車協調或端對端 RL。障礙物以 2D 雷射掃描平面可偵測者為主；動態障礙物與長期運作列為後續延伸。

### 1.7 章節安排

第 2 節回顧 LLM 機器人代理、語言導航、澄清與安全護欄，以及模組化導航與評測的相關研究，並指出研究缺口；第 3 節說明系統架構與演算法；第 4 節為實驗設計；第 5 節討論限制與後續工作。
