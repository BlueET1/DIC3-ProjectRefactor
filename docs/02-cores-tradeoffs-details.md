# 02. 5 Cores · 3 Trade-offs · 10 Details

本頁把期中提案的 Deep Research（五個核心思維、三個研究爭論、十個深度問題）重構成「原則 → 設計決定 → 可驗證規格」，並標出每一項對應到 OpenSpec 的哪個 capability／requirement（見 [`openspec/`](../openspec/)）。

---

## 5 Cores（五個核心原則）

| # | 核心原則 | 一句話 | 設計決定 | 對應 spec |
|---|---|---|---|---|
| C1 | **定位是有不確定性的估計** | 位置與朝向不是真值；打滑、重複環境、延遲都會讓估計偏離 [4][5] | 派送前檢查定位與 TF 時效；異常就不出發 | `robot-readiness` |
| C2 | **感測不到 ≠ 沒有障礙物** | 2D LiDAR 只看掃描平面，有遮蔽、無效值與中斷 [8] | 感測過期或無效時禁止派送；實驗只用掃描平面可見障礙物並揭露盲區 | `robot-readiness` |
| C3 | **路徑可行性要考慮車身與運動限制** | 小車不是點；中心線可過不代表車身可過 [9] | 使用核對過的 footprint；Agent 不得修改 footprint 或安全參數 | `navigation-dispatch` |
| C4 | **語意任務與即時控制分層** | Agent 決定去哪、要不要問、怎麼回報；Nav2 決定怎麼走與何時停 [2][4] | LLM 只能提出白名單工具呼叫；不能輸出座標或輪速；停止不等 LLM | `task-intent-parsing`、`navigation-dispatch` |
| C5 | **可靠性來自重複測試與失敗分析** | 單次成功不代表換場景仍可靠 [6][7][12] | 語言層、導航層、回報層分開評估；保留所有失敗與逾時 | `mission-reporting`（事件紀錄是評估資料來源） |

## 3 Trade-offs（三個設計取捨）

### T1 模組化導航 vs. 端對端學習

| | 模組化（Nav2） | 端對端（RL／學習策略） |
|---|---|---|
| 優點 | 責任清楚、易除錯、工具成熟 [4] | 可從資料學習感測→動作，複雜場景可減少人工設計 [7] |
| 缺點 | 參數調校多，複雜場景仍會失敗 [6] | 泛化邊界與失敗模式難界定，實機轉移成本高 |
| **本專題選擇** | ✅ **固定 Nav2 當底層**，只研究任務層 Agent 的增益 | 不訓練 RL；這是讓「Agent 增益」可被單獨量測的前提 |

### T2 預建地圖 vs. 無地圖導航

| | 預建地圖 + 命名地點 | 無地圖／局部感測 |
|---|---|---|
| 優點 | 有全域空間關係，命名地點與長距離規劃容易 [5] | 不需事先建圖，適合探索或環境變動 [6][12] |
| 缺點 | 地圖會過時 | 缺全域資訊，可能陷入死巷 |
| **本專題選擇** | ✅ **預建地圖 + 地點表 + 即時 costmap**；陌生地點由 Agent 澄清，不讓 LLM 猜座標 | 列為後續延伸 |

### T3 保守安全距離 vs. 通行效率

| | 保守（低速、大 inflation） | 積極（高速、小距離） |
|---|---|---|
| 優點 | 容納定位、控制與反應延遲誤差 | 窄路可通行、完成時間短 |
| 缺點 | 窄路被判無路、停滯、繞行 | 碰撞風險上升 [6][9] |
| **本專題選擇** | ✅ **固定一組經實測的保守設定**；以碰撞、到達率、時間、最小淨距共同評估 | 參數敏感度列為選配實驗；Agent 行駛中不得改參數 |

另外，本專題自己的系統設計也存在一個取捨，記錄於 OpenSpec `design.md`：

> **T★ 澄清與檢查 vs. 互動延遲**：B2 的澄清與狀態檢查預期降低不當派送，但會增加回合數與延遲。RQ3 就是要量化這個代價。

## 10 Details（十個深度問題 → 實作細節）

每題寫出「判斷重點」與「落到規格的地方」。評分方式：是否解釋原因、提出可觀察證據、說明取捨，各題 0–2 分，共 20 分（組內理解檢查，不是實驗成績）。

| # | 問題 | 判斷重點 | 落到哪裡 |
|---|---|---|---|
| D1 | 輪子轉但小車卡住，里程計和真實位置會怎樣不同？ | 輪式里程計持續累積位移；要交叉比對雷射、定位、TF。不能只靠輪速判斷有進度 | `mission-reporting`：ARRIVED 需 action 成功 **且** 觀測終點姿態 |
| D2 | 地圖正確但車沿牆偏移，是定位錯還是控制問題？ | 先看時間戳與 map→odom→base_link、雷射對齊，再看 footprint、costmap、控制回饋 | 事件紀錄需含 pose、TF 狀態與時間戳 |
| D3 | LiDAR 顯示沒障礙，為何仍撞到桌子？ | 桌面不在掃描平面；遮蔽、無效值、資料過期 | `robot-readiness`：感測過期即 NOT_READY；實驗揭露盲區 |
| D4 | 中心線能過窄門，規劃器為何拒絕？ | footprint、姿態、地圖解析度、inflation 都影響；要量實際淨寬，不能縮小 footprint | `navigation-dispatch`：Agent 不得修改 footprint |
| D5 | 規劃後出現新箱子，哪個模組先反應？ | 底層感測／停止與 Nav2 先處理；Agent 監控結果，不等 LLM 才停 | `navigation-dispatch`：低延遲停止獨立於 LLM |
| D6 | 擴大 inflation_radius 必然更安全？ | 改的是代價場，不保證實際淨距；可能造成無路可走 | T3；實驗量碰撞、淨距、到達率、時間 |
| D7 | 快方法偶爾碰撞、慢方法沒觀察到碰撞，怎麼比？ | 固定任務與樣本數，報碰撞率與信賴區間；沒觀察到 ≠ 零風險 | 評估：Wilson 95% CI |
| D8 | Gazebo 成功、實機失敗，先查什麼？ | 感測頻率、延遲、里程計誤差、打滑、車身尺寸、時間來源（use_sim_time） | 模擬與實機結果分開記錄、分開報告 |
| D9 | 怎麼證明 Agent 有幫助，而不是 Nav2 本來就會走？ | 固定 Nav2，比較 B0／B1／B2；分開量地點解析、澄清、不當派送、完成、回報 | 評估設計（RQ1–RQ3） |
| D10 | 「去門口」有兩個門口，或途中取消，怎麼辦？ | 歧義先問、不派送；取消優先，要確認 action 取消結果，不能把取消當到達 | `task-intent-parsing`（CLARIFY）、`navigation-dispatch`（cancel）、`mission-reporting` |
